# СКИФ-48 · дашборд телеметрии сева

Прототип BI-дашборда по выгрузке телеметрии сеялки из **Fort Monitor** (объект 12917, СКИФ-48 Эл.Доз).

Карта с треком движения в **двух слоях** (переключатель в сайдбаре):

- **«Забитие сошников»** — зелёный на участках без забития; там, где сошники забиты, цвет идёт по градиенту от **жёлтого** (один забитый) через **оранжевый** к **красному** (все 32);
- **«Отклонение нормы»** — зелёный, пока отклонение фактической нормы от номинальной в пределах порога (по умолчанию 5 %), дальше градиент до красного (20 % и выше). Недолив и перелив красятся одинаково: считается модуль отклонения.

Рядом — показатели за выбранный интервал: доля пробега без забития, площадь, пробег, а также **по каждому бункеру** средняя норма сева, номинальная норма и отклонение от номинальной. Процентные индикаторы подкрашиваются по трём уровням, которые задаёт пользователь.

История правок — в [CHANGELOG.md](CHANGELOG.md).

Расчёт нормы и найденные дефекты вынесены в
[`docs/seed-rate-calculations.md`](../../docs/seed-rate-calculations.md) —
тот же материал в применении к `mart` и DataLens: формулы, контрольные
числа, готовые запросы и список того, что в БД доделать.

## Что показывает

| Показатель | Формула | Единица |
|---|---|---|
| Площадь | `Σ ΔПлощадь_га` | га |
| Общий пробег | `Σ (ΔПробег_м × 101_7_Кол-во_сошников)` | м·рядков |
| Пробег с забитием | `Σ (ΔЗабитие_на_рядок × кол-во забитых рядков)` | м·рядков |
| Доля с забитием | Пробег с забитием / Общий пробег × 100 | % |
| Доля без забития | 100 − доля с забитием | % |
| Средняя норма сева · Бункер N | `Σ ΔМасса_бN_кг / Σ ΔПлощадь_га` | кг/га |
| Номинальная норма · Бункер N | площадно-взвешенное среднее `Норма_номинал_бN` | кг/га |
| Отклонение от номинальной · Бункер N | `(средняя норма − номинал) / номинал × 100` | % |

**Про местрочные единицы.** «Общий пробег» — это метраж пути, умноженный на число рядков, то есть *метро-рядки*. Обе величины в одних единицах, поэтому их отношение — корректная доля, без приведения.

**Про цвета.** Пороги задаются по шкале **качества** (доля без забития, где больше = лучше). Доля *с* забитием оценивается зеркально: зелёный, если забитие ≤ 100 − порог. Иначе индикаторы врали бы в разные стороны — 0,04 % забития всегда было бы «хорошо», а 99,96 % качества всегда «плохо».

**Про норму.** Показатели выводятся **по каждому бункеру отдельно**. Суммарное отклонение скрывает локальный сбой: перелив одного дозатора и недолив другого дают в сумме ноль, а на карте в этот момент ничего не происходит. На объекте 12917 настроены два бункера (УДПВ1 и УДПВ2), поэтому под первой строкой показателей — ровно один ряд из шести карточек: три на бункер.

Каждая величина считается от **сумм** (Σмасса / Σплощадь), а не усреднением построчных значений: простое среднее взвешивает группы по числу строк, а не по площади и из-за строк простоя даёт около +14 % вместо фактических −0,2 %. Номинал взвешивается по площади — так контроль совпадает с формулой из `build_dataset.py`, которая печатает сводную цифру и по каждому бункеру отдельно.

Построчная же `Норма_динам` усредняется по шагам накопленной площади окном 0,5 га: площадь в выгрузке обновляется только в 8 % строк, поэтому отношение масса/площадь в пределах одной строки делится на ноль, а скользящее окно по строкам смещено на 3 п.п. из-за неравномерности пробега.

### Раскраска трека на карте

Слой выбирается в сайдбаре, у каждого свой набор подсказок и своя легенда.

#### Слой «Забитие сошников»

Цвет сегмента трека зависит от числа **одновременно забитых сошников** — счётчик собирается из 32 пофакторных флагов `221…224`, по одному на каждый сошник машины:

| Забито сошников | Цвет |
|---|---|
| 0 | зелёный `#1a9850` |
| 1 | жёлтый `#e6b800` |
| 16 (середина шкалы) | оранжевый |
| 32 (максимум) | красный `#d63129` — совпадает с прежним красным |

Цвета интерполируются в HSL по каналу оттенка, а не в RGB: иначе середина шкалы выходит грязно-коричневой, а не чистым оранжевым. На максимуме шкалы цвет совпадает с прежним `COLOR_BAD`, поэтому худшие участки выглядят как раньше.

Сегмент красится по состоянию в его **конечной** точке: забитие фиксируется в момент замера, значит участок, приведший к этому замеру, и есть участок с забитыми сошниками. Подряд идущие сегменты с одинаковым числом забитых склеиваются в одну ломаную (~49 тыс. точек превращаются в ~240 объектов карты).

#### Слой «Отклонение нормы»

Цвет сегмента — по **модулю** отклонения, но берётся оно не сводное, а **максимальное по модулю среди бункеров**. Это главное отличие слоя: суммарное отклонение скрывает локальный сбой (перелив одного дозатора и недолив другого дают ноль), а по максимальному участок с вышедшим за порог бункером на карте виден. В подсказке при этом указан, какой именно бункер дал цвет («Бункер 2: отклонение −24.0 %»).

Пороги (по умолчанию 5 % и 20 %) задаются в сайдбаре:

| Модуль отклонения | Цвет |
|---|---|
| ≤ зелёного порога | зелёный `#1a9850` |
| между порогами | градиент зелёный → жёлтый → красный (HSL по оттенку) |
| ≥ красного порога | красный `#d73027` |
| норма не определена | серый `#9aa5b1` |

Отклонение квантуется **в корзины по порогам**, а не в абсолютные значения: своя корзина у зелёной зоны, 10 ступеней внутри градиента, своя у красной. Цвет корзины берётся в середине её диапазона (`rate_bucket_color`), поэтому полоса легенды и цвета трека совпадают один в один.

Такая квантизация нужна по той же причине, по которой в слое забития сегменты группируются по счётчику: без неё зелёная зона, где лежит 43,5 тыс. строк из 49,4 тыс., распалась бы на десятки разных ключей — трек разошёлся бы на 682 ломаные вместо ~180 и перестал бы склеиваться.

В попапе ломаной — **по строке на каждый бункер**: своя динамическая норма против своего номинала и своё отклонение, на **середине** сегмента (так цифра ближе к тому, что показано цветом, чем значение в крайней точке). Сводной строки в попапе нет — она и есть то, что маскирует сбой.

## Почему дельты считаются скриптом, а не в BI

Fort Monitor отдаёт **только накопительные счётчики**: `151_22` площадь, `151_23` пробег, `153_28` забивание. Показать их можно только через дельты.

Счётчики перезапускаются на ноль. Наивная разность в момент сброса даёт скачок −1786, а `ABS()` превращает его в фантомные +178,6 га, которые попадут в `SUM()`. Поэтому дельты считает `scripts/make_delta_columns.py`:

- ведётся **высокая отметка** отдельно по каждому счётчику;
- откат глубже половины отметки — **сброс**: начинается новая эпоха, дельта в этой строке 0;
- откат мельче половины — **шум передачи**: дельта 0, отметка не двигается.

Порог «глубже половины» разделяет помехи однозначно: на объекте 12917 шумовые откаты площади были 1…6 условных единиц при настоящем сбросе 1786.

### Те же правила — по счётчикам массы

`build_dataset.py` считает массу из счётчиков дозаторов `151_24…151_27` той же логикой, но со своими порогами (`counter_delta`): прирост идёт от **бегущего максимума**, падение дальше чем на 10 % — перезапуск и сдвиг базы, мельче — шум, база стоит.

Зачем это отдельно: в окнах, где выгрузка отдаёт построчно чередование двух последовательностей (`88149, 88018, 88161, 88022, …`), старая формула `diff()` с отсечением минусов дважды считала один и тот же рост — ложный прирост ~140 импульсов на строку. По сумме это 4 группы с отклонением 400…2100 % и +2,4 % к общей норме.

Конфигурация дозатора (`104_12…104_19`) в 154 строках приходит нулём — это пропавший снимок, а не выключенный дозатор: счётчик в эти строки растёт, а масса молча терялась. Нулевые значения заменяются последней известной конфигурацией (`last_known_config`).

Номинал в группе усредняется **по ненулевым строкам**: в первые минуты работы номинал приходит нулём, и обычное среднее занижало группу до 122,78 кг/га вместо 200,28.

После всех трёх правок контроль нормы сошёлся: **199,85 кг/га против номинала 200,28 — отклонение −0,22 %** (было +1,63 %).

### Колонки по каждому бункеру

Расчёт идёт **послойно по дозаторам**, а не только суммой. Для каждого настроенного бункера в CSV пишется четыре колонки: `ΔМасса_бN_кг`, `Норма_номинал_бN`, `Норма_динам_бN`, `Откл_бN`. Сводные четыре (`ΔМасса_кг`, `Норма_номинал`, `Норма_динам`, `Откл_нормы`) остаются — на них опирается самоконтроль скрипта.

Что для этого нужно: масса и номинал каждого дозатора считаются отдельно, группы (окно 0,5 га) берутся те же общие, потому что мера группировки — накопленная площадь, а она одна на машину. Нулевые по номиналу дозаторы колонок не получают: на объекте 12917 УДПВ3 и УДПВ4 не настроены, и индикаторы для них превратились бы в пустые карточки. Число бункеров приложение определяет по именам колонок, а не по константе.

Контроль печатается сводный и по каждому бункеру:

```
Контроль нормы, Свод:     199.85 кг/га против номинала 200.28 (отклонение -0.22 %)
Контроль нормы, Бункер 1:  64.96 кг/га против номинала  65.09 (отклонение -0.21 %)
Контроль нормы, Бункер 2: 134.89 кг/га против номинала 135.19 (отклонение -0.22 %)
Настроено бункеров: 1, 2
```

### Проверка, которая не даёт ошибиться

```
ΔПлощадь_га × 10000 / ΔПробег_м  ==  ширина захвата
```

На 12917 ширина приходит как `101_8_ШиринаЗахвата_ПК = 60`, то есть 6,0 м. Инвариант сошёлся в **6,0000 м**. Если после правки расчёта он разъезжается — сломаны дельты, а не данные.

Скрипт печатает этот инвариант после каждого прогона.

## Структура

```
streamlit_app.py                 приложение (точка входа для share.streamlit.io)
requirements.txt                 зависимости с зафиксированными версиями
data/
  telemetry_skif48.csv           набор данных: 49 373 строки, 51 колонка
scripts/
  make_delta_columns.py          расчёт дельт с защитой от сброса через ноль
  build_dataset.py               xlsx → csv (с самопроверкой инварианта)
  sanitize_for_public.py         обезличивание перед публикацией
```

### Почему CSV, а не xlsx

| Формат | Чтение pandas | Размер |
|---|---|---|
| исходный xlsx (81 колонка) | ~21,6 с | 13,4 МБ |
| `telemetry_skif48.csv` (51 колонка) | **0,15 с** | 12,1 МБ |

На бесплатных хостингах (включая share.streamlit.io) 22 секунды на первую загрузку — это очень заметно. CSV читается более чем в 140 раз быстрее.

```bash
# 1. посчитать дельты в исходной выгрузке

python scripts/build_dataset.py <исходный_с_дельтами.xlsx> data/telemetry_skif48.csv
```

## Данные

В наборе — **рабочее поле заказчика, в исходных координатах, намеренно**. Демонстрация идёт клиенту, и он должен видеть свои ориентиры и наименования: со сдвинутым треком первая же претензия будет «вы показываете не наше оборудование».

Что реально лежит в файле:

| Есть | Нет |
|---|---|
| координаты поля заказчика | идентификаторов объектов и компаний |
| даты и время работы техники | названий хозяйств и групп объектов |
| счётчики и флаги забивания | данных других клиентов платформы |

Набор собран из **одной** машины (объект 12917), посторонних записей в нём нет — проверено.

Два практических замечания по доступу:

- **GitHub** — сделайте репозиторий приватным. Даже если в нём нет чужих данных, история коммитов сохраняет всё, что попадало в файлы раньше.
- **share.streamlit.io** — приложения из публичного сообщества доступны **любому, у кого есть ссылка**, и закрытого варианта у площадки нет. Отправьте ссылку клиенту напрямую, не публикуйте её в общих каналах.

На случай, если этот же набор когда-нибудь понадобится для публичного показа не клиенту, рядом лежит необязательный `scripts/sanitize_for_public.py`: сдвигает координаты на ~2,3 км и округляет до 4 знаков, показатели при этом не меняются (это сдвиг, а не масштаб). Даты он не трогает.

## Ограничения прототипа

- **Один объект и один тип машины.** СКИФ-48 Эл.Доз. Другие типы (СКИФ-38, СКИФ-Т06, ISOBUS) требуют своей карты привязки датчиков к параметрам.
- **Семантика `153_28` не подтверждена.** По документации проекта это сумма метро-сошников, то есть при нескольких забитых рядках метраж суммируется. Нужна оговорка от заказчика, прежде чем считать долю забивания производственным показателем.
- **Один период загрузки.** 49 273 точки покрывают 09–16.10.2026.
- **Битовая маска забивания не используется.** `13_1_*` / `13_2_*` в 98,7 % строк нулевые — проверить показатели по ним нельзя.
- **Карта подгружает тайлы OpenStreetMap** при каждом открытии.
